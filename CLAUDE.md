# jr — Jira CLI

A Rust CLI tool for automating Jira Cloud workflows. Binary name: `jr`, package name: `jr`.

## Architecture

Single-crate thin client wrapping Jira REST API v3 and Agile REST API directly with reqwest. No generated client or intermediate abstraction layer.

## Conventions

- **Commits:** Conventional Commits format (`feat:`, `fix:`, `docs:`, `chore:`, `ci:`, `test:`)
- **Branches:** `type/short-description` (e.g., `feat/issue-commands`, `fix/auth-flow`). Default branch is `develop`. Feature branches → PR to `develop` → PR to `main` for releases.
- **Protected branches:** `main` and `develop` require CI to pass and code owner approval on PRs. Admins can bypass.
- **`strict: false` on both protected branches — tested tree ≠ merged tree (ADV-P50-MED-002, documented not changed, round 20):** Neither `main` nor `develop`'s branch-protection rule requires a PR branch to be up to date with its base before merging (`required_status_checks.strict` is `false` on both). Consequence: `ci-gate`'s green result is computed against the base branch's state AT THE TIME the check last ran on that PR — not re-validated against the base branch's current tip immediately before merge. A PR opened against `develop` at commit A, whose gate went green there, can still merge cleanly even after `develop` has since moved to commit B — the code that actually lands on `develop` is the PR branch merged onto B, a combination that was never itself CI-tested. This is a real, observed condition, not a hypothetical: during this same session PR #667 sat green against a stale `develop` until it was manually reconciled with `develop`'s current tip before merge. Practical implication for anyone merging a PR that has been open for a while: re-run (or at least re-check the age of) the gate if `develop`/`main` has moved meaningfully since the PR's last green run, rather than trusting an old green check by itself. **Do not flip `strict: true` without the human's explicit sign-off** — it is a repo-wide merge-behavior change (every PR would need a rebase/merge-commit-and-rerun cycle before merging, not just this repo's CI-gate machinery), and that decision is intentionally still pending, not made by this note.
- **CI Gate — SCOPE SUMMARY (current state; full round-by-round adversarial-review history — round 1 through the S-CIGATE-3 landing and its fix-bursts 3–8 — extracted to `docs/specs/ci-gate-completeness.md`; read it before touching any of the six files below):**
  **Enforced:** decision semantics (behavioral subprocess tests against `scripts/check-ci-gate.sh`) · assertion shapes (job/step key sets, `if:`/env value pins — set-equality, default-deny) · value substitution (byte-for-byte pins, fail LOUD on anything unnormalizable) · non-LF YAML line breaks (CR, NEL, LINE SEPARATOR, PARAGRAPH SEPARATOR) · YAML node properties on a pinned key in the `ci-gate` job block (`&anchor`/`!tag`/`!!tag` prefixing a mapping key), caught structurally via a real event-stream parse (`tests/common/wf.rs::find_key_node_properties`, S-CIGATE-3).
  **NOT enforced:** `uses:` VALUES on the `ci-gate` decision path (its two `uses:` steps are unpinned — a `$GITHUB_ENV`/`$GITHUB_PATH`/sudo residual, detail in the extracted history); the node-property class for jobs OTHER than `ci-gate`; human judgment on `ALLOWED_SKIPS`/`PINNED_ALLOWED_SKIP_IF_EXPRESSIONS` pin updates; the sharded mutation gate's untrusted-`outcomes.json` residual (`mutants-aggregate.sh` trusts data produced inside the same `mutants` shard job's build/test loop — blast radius is the mutation-quality signal only, no secret/`GITHUB_TOKEN` exposure) and a sibling artifact-name-pattern spoof residual (shard-status/outcomes artifacts are matched by name, not job provenance). See `docs/specs/cargo-mutants-policy.md`'s "Sharded Gate: Residual Trust Boundary" section.
  **Control for the unenforced:** code review of the `ci.yml` diff, scoped to `uses:` VALUES and `ALLOWED_SKIPS`/pin-literal human judgment.
  **Durable fix — LANDED (S-CIGATE-3, 2026-08-11), not merely re-promised:** `ci.yml` is parsed once with a real YAML parser (`saphyr-parser = "=0.0.11"`, exact pin, `[dev-dependencies]` only — never enters the `msrv` job's lib+bin compile scope) via `tests/common/wf.rs`'s spanned document model over the low-level `Parser`/`Event` stream (never the higher-level `saphyr::Yaml`/`YamlLoader` API); structural assertions query the parsed tree, and today's byte-for-byte scalar pins are retained as a second layer sourced from parsed `Event::Scalar` values (each additionally asserts `ScalarStyle::Plain` so re-quoted forms aren't silently accepted). The round-14 non-LF byte scan is retained unconditionally as an independent third layer — NOT subsumed by the parser, since `saphyr-parser` is YAML-1.2-conformant (NEL/LINE SEPARATOR/PARAGRAPH SEPARATOR are correctly not line breaks under 1.2, only under YAML 1.1). What this does NOT close: `scripts/check-ci-gate.sh`'s runtime `toJSON(needs)` evaluation (never parsed `ci.yml`, out of scope); the sudo bound and the two unpinned `uses:` values on the decision path.
  **Review scope is SIX files, not one:** `.github/workflows/ci.yml`, `scripts/check-ci-gate.sh`, `tests/ci_gate_completeness.rs`, `tests/common/wf.rs`, `scripts/lib/trusted-jq.sh` (the single shared jq resolver for both `check-ci-gate.sh` and `mutants-aggregate.sh`), and `scripts/mutants-aggregate.sh` (the `ci-gate.needs` proxy replacing the old single `mutants` job) — all PR-supplied and executed from that PR's own checkout; no repository check compares any of the six against an outside-the-tree reference. Code review of a `ci-gate`-touching PR must cover the diff across all six together.
  ---
  `ci-gate` (job name "CI Gate") is THE single required branch-protection status check on `develop`/`main`. New CI jobs that must be required go into `ci-gate.needs`, never wired directly into branch protection (prevents the matrix-rename fragility class, DEC-096/DEC-097). `ci-gate`'s pass/fail decision is fail-closed (`scripts/check-ci-gate.sh`, S-CIGATE-2): every job in `needs` must report `success`, except jobs named in `ALLOWED_SKIPS` (currently EMPTY — `mutants-aggregate` runs `if: always()` with an internal Step-0 no-op and never reports `skipped`; no `ci-gate.needs` member currently needs skip-tolerance), which may additionally report `skipped`; any other result fails the gate by default. A job added to `ci-gate.needs` that can legitimately report `skipped` must ALSO be added to `ALLOWED_SKIPS` with a human-reviewed, byte-identical pin in `tests/ci_gate_completeness.rs::PINNED_ALLOWED_SKIP_IF_EXPRESSIONS` (currently EMPTY — `&[]`) — `ALLOWED_SKIPS` membership alone is not the trust boundary; the pinned-literal mechanism is what makes a skip-tolerance grant reviewable and decidable rather than pattern-matched. Full mechanism history, every closed bypass, and the exact residuals: `docs/specs/ci-gate-completeness.md`.
- **Errors:** Always suggest what to do next. Map to exit codes via `JrError::exit_code()`
- **Output:** `--output json` returns structured JSON for both success and errors. Human text is default.
- **JSON render invariant (#526):** Every `--output json` path in `src/cli/` MUST route through `output::render_json` or `output::print_output` (which delegates to `render_json`). Direct `serde_json::to_string_pretty` calls and compact `serde_json::json!` Display printing are both forbidden. Output is pretty-printed. As of v0.6+ (#526), `jr issue create --request-type` and `jr project fields` changed from compact to pretty-printed JSON; `jq` and programmatic parsers are unaffected.
- **Non-interactive:** `--no-input` disables prompts (auto-enabled when stdin is not a TTY). Commands must have fully non-interactive flag equivalents.
- **Idempotent:** State-changing commands (move, assign) exit 0 if already in target state.
- **Tests:** TDD. Unit tests inline, integration tests in `tests/`. Property tests with proptest. Snapshot tests with insta.
- **No unsafe code** without explicit justification in a comment.
- **No lint suppression without refactoring.** If clippy warns (e.g., `too_many_arguments`), refactor to fix the root cause — don't add `#[allow]`. If refactoring is impractical, ask the user before suppressing and include a justification comment.
- **No let-chains.** `if let … && …` / `… && let …` syntax requires Rust ≥1.88 with edition 2024; MSRV is 1.85. Use nested `if` blocks instead. The `msrv` CI job catches violations in lib + bins; inline `#[cfg(test)]` modules in `src/` and integration tests in `tests/` are both outside its enforceable scope (see the `ci.yml` msrv scope comment). Temporary — delete this entry and the three citing in-code comments when MSRV is raised to ≥1.88.
- **Default to fixing code, not tests.** When a test fails, assume the test is correct and fix the implementation using idiomatic Rust. Only modify a test when requirements have changed — not to accommodate non-idiomatic code or lint workarounds.
- **Test naming:** New tests use `test_<verb>_<subject>_<expected_outcome>` (e.g., `test_auth_switch_returns_json_ok`). Existing tests are NOT renamed for style alone — but a name asserting a guarantee its body doesn't check is a defect, not a style deviation, and may be corrected independently. See `docs/specs/test-naming-convention.md`.
- `--dry-run` is implemented on `issue edit` (multi-key positional + `--jql`-resolved sets) with `--output json` support. Pre-PR2 NFR-O-C originally documented this as DOCUMENT-AS-IS-OUT-OF-SCOPE; superseded by issue #110 part 2.
- `jr version --output json` is not implemented (NFR-O-X: deferred to v2; consider for `release-notes` automation).
- `sprint list` table omits start/end dates (NFR-O-U: deferred UX pass v2; available in API response).
- `auth status` has no `--output json` support (NFR-O-N: deferred; neither single-profile nor multi-profile JSON is implemented — `src/cli/auth/status.rs::status()` writes human text only via `println!`). JSON path planned alongside future `auth list --output json` extension.
- JSON output has no `_meta: {version: N}` envelope (NFR-O-P: deliberate for v0.5; consider for v2 to enable downstream-parser schema-drift detection).

### Output channels

CLI handlers follow one of five output-channel profiles:

1. **Pure** — stdout only (JSON or table data); no stderr output at all.
2. **Read-only** — stdout for data, stderr for hints/warnings (e.g., truncation notices, "showing N of M").
3. **Mixed** — stdout for success data, stderr for errors and hints; applies to most read commands.
4. **Symmetric** — stdout for `--output json`, stderr for human-readable errors in either mode; state-changing commands that also print a result use this profile.
5. **No-log facade** — state-changing commands that emit only a JSON result on stdout (e.g., `{"key": "FOO-123"}`); no progress or logging to stderr.

The distinction matters for scripting: pipe stdout for data, redirect stderr for diagnostics. Never write diagnostic text to stdout in profiles 1/2/3/5.

## Gotchas

- **`rust-toolchain.toml` outranks `rustup default` — msrv job requires `RUSTUP_TOOLCHAIN` env (S-626-1):** When `rust-toolchain.toml` is present in the working directory (as it is in this repo, with `channel = "stable"`), it outranks `rustup default` in rustup's precedence chain. Rustup precedence, highest to lowest: `+toolchain` > `RUSTUP_TOOLCHAIN` env > directory override (`rustup override set`) > `rust-toolchain.toml` > `rustup default`. (Note: directory overrides and `rust-toolchain.toml` are additionally ranked by proximity to cwd — a nearer file beats a farther override — but this is immaterial in CI where no directory override exists.) The pre-fix `msrv` CI job pointed at the tip of dtolnay's `1.85.0` version branch, which hard-codes the toolchain version and has no `toolchain` input declaration. The action correctly installed 1.85.0 and set it as `rustup default`. `cargo check` then ran in the repo root where `rust-toolchain.toml` (`channel = "stable"`) outranked `rustup default`, so the check silently ran under stable — a false-green. Because the old SHA had no `toolchain` input, adding `with: {toolchain: "1.85.0"}` alone would have been silently ignored by GitHub Actions (at most an "Unexpected input(s)" warning); the SHA replacement to `fa04a1451ff1842e2626ccb99004d0195b455a88` was a hard prerequisite — this version of the action declares `toolchain` as a required input. The fix adds both `with: {toolchain: "1.85.0"}` (to install the correct toolchain) AND `env: {RUSTUP_TOOLCHAIN: "1.85.0"}` on the `cargo check` step — `RUSTUP_TOOLCHAIN` outranks `rust-toolchain.toml`, ensuring cargo uses 1.85.0 at check time. Both are load-bearing — the action input installs the toolchain; the env override ensures `cargo check` uses it. Omitting the env override silently reverts to stable validation. Note: at the currently pinned SHA (`fa04a1451ff1842e2626ccb99004d0195b455a88`), the action validates `toolchain:` as a hard-required input — dropping the `with:` block fails the job loudly. The only genuinely silent revert vector is removing the `RUSTUP_TOOLCHAIN` env override.
- **Windows config/cache paths (BC-6.1.014, BC-6.2.016):** On Windows, `jr` uses idiomatic AppData locations — config at `%APPDATA%\jr` (Roaming, via `dirs::config_dir()`) and cache at `%LOCALAPPDATA%\jr` (Local, via `dirs::cache_dir()`). Unix paths (`~/.config/jr`, `~/.cache/jr/v1/<profile>/`) are unchanged. The `JR_CONFIG_DIR`/`JR_CACHE_DIR` debug seam (Decision 5, ADR-0016) provides cross-platform test isolation; `XDG_CONFIG_HOME`/`XDG_CACHE_HOME` remain Unix-only.
- **Windows Credential Manager isolation (SEC-WCM-DOC):** On Windows, `jr` stores OAuth tokens and API tokens via the `keyring` crate's `windows-native` feature, which uses Windows Credential Manager (`CRED_TYPE_GENERIC` entries). Secrets stored there are accessible to any process running in the same user session — the same security posture as `gh` and `git-credential-manager`. OS-level user-session isolation is the trust boundary on Windows. Do not use `jr` in a shared-session environment (e.g., a shared Windows terminal server) without understanding this posture. **DPAPI-encrypted-file fallback for oversized OAuth tokens (ADR-0021, S-cycle4-dpapi-storage-fix, issue #759):** Windows Credential Manager caps a single credential blob at ~2560 bytes, which some Atlassian OAuth refresh tokens exceed. When `store_oauth_tokens` hits that ceiling (`keyring::Error::TooLong`), the whole access/refresh pair falls back to a user-scope, DPAPI-protected file at `%LOCALAPPDATA%\jr\secrets\<profile>\oauth-tokens.dat` instead of failing the login — the same OS-level user-session trust boundary applies (DPAPI-protect is user-scoped, `CRYPTPROTECT_UI_FORBIDDEN`, never machine-scope). The pair is always stored entirely in one backend (never split across keyring and DPAPI-file), and a pre-existing keyring pair is deleted before the DPAPI write so a crash mid-fallback can't leave a stale pair shadowing the fresh one. This fallback is engaged only past the keyring's size ceiling; a token that fits is stored in Windows Credential Manager exactly as described above. **Verification status (DEC-335):** the routing/path/envelope logic is implemented and unit-tested cross-platform, but the actual `CryptProtectData`/`CryptUnprotectData` FFI round-trip cannot be exercised on a non-Windows development host — per `src/api/auth_windows_store.rs`'s module header, real-Windows verification of that round-trip is a pending F4 CI/manual-smoke-test item, not yet a proven on-every-PR fact.
- **jr.exe requires an explicit 8 MB main-thread stack on Windows (WIN-STACK):** Windows PE headers default to a 1 MB main-thread stack, while Linux/macOS default to 8 MB. The `#[tokio::main]` async runtime + clap dispatch + result rendering exceed 1 MB, causing jr.exe to crash on normal commands like `jr issue list`. The fix is embedded at compile time via `.cargo/config.toml` under `[target.x86_64-pc-windows-msvc]`: `rustflags = ["-C", "link-arg=/STACK:8388608"]` — this sets an 8 MB reserve in the PE header. Unix builds are unaffected. `RUST_MIN_STACK` is NOT a valid fix: it only affects `std::thread::spawn` threads (test-harness workers), not a process's main thread.
- **Multi-profile boundary:** every cache reader/writer takes `profile: &str` as its first arg. Pass `&config.active_profile_name` from any handler that has `&Config` in scope. Cross-profile cache leakage is a correctness bug, not a UX issue — sandbox vs prod custom-field IDs can differ.
- **Per-profile vs shared keychain keys (S-cycle3-percred-storage, BC-1.4.031):** `email` and `api-token` are namespaced per-profile as `<profile>:email` / `<profile>:api-token` (`store_api_token`/`load_api_token`, `src/api/auth.rs`), symmetric with the existing `<profile>:oauth-access-token` / `<profile>:oauth-refresh-token` namespacing — both are cloudId/profile-scoped, not account-level. Only `oauth_client_id`/`oauth_client_secret` remain flat keychain keys (account-level, shared across profiles). There is deliberately no legacy-flat-key fallback for `email`/`api-token` on any profile, including `"default"` — that's a difference from the OAuth keys, whose `"default"` profile still lazy-migrates legacy flat keys on first read. **Wired up (S-cycle3-remove-logout-semantics, BC-1.2.013/BC-1.2.014):** `auth remove` (`src/api/auth.rs::clear_profile_creds`) now clears BOTH the OAuth pair and the namespaced `<profile>:email`/`<profile>:api-token` pair. `auth logout` (`src/cli/auth/logout.rs::handle_logout`) intentionally does NOT clear the api-token pair — it clears only the OAuth pair via `clear_profile_oauth_pair`, staying non-destructive for API-token profiles. **On an api-token profile specifically (DEC-322), `auth logout` no longer silently no-ops** — it prints an informational, non-error stderr notice (`"This profile uses API-token auth — nothing to log out; use `jr auth remove <profile>` to delete stored credentials."`) and exits 0; the api-token pair itself is left completely untouched. This notice is stderr-only and never appears on stdout in any output mode, including `--output json` (the JSON payload shape is unchanged from the pre-DEC-322 no-op behavior). **`auth refresh` clears nothing before re-obtaining credentials (S-cycle3-chosen-flow-reconcile, BC-1.2.051 Invariant 2, I-6, "relogin-then-replace"):** `src/cli/auth/refresh.rs::refresh_credentials` no longer calls any clear function up front — it calls `login_token`/`login_oauth` directly, which resolve/obtain the new credential value FIRST and only then persist it via `auth::store_api_token`/`auth::store_oauth_tokens` (an unconditional overwrite of the existing keychain entry). A refresh that fails to obtain a usable replacement therefore leaves the profile's existing credentials completely untouched. This replaced the prior "clear-then-login" sequence, which called `clear_profile_oauth_pair` (OAuth) before login — see the CHANGELOG `[Unreleased]` entry for DEC-321 for the full before/after. **Narrow, documented exception (S-cycle4-honest-fail-message, BC-1.4.039, PR #771 review Finding NB-2):** when `refresh_oauth_token_with_url`'s post-refresh `store_oauth_tokens` call fails with a `DpapiFallbackFailed` marker (Windows-only — BOTH Credential Manager AND the DPAPI-encrypted-file fallback failed to store the new pair), the refresh path proactively clears the profile's stored OAuth pair via `clear_profile_oauth_pair` as part of returning the honest-fail error, rather than leaving it untouched. This is deliberate, not a violation of "relogin-then-replace": the single-use refresh token has already been consumed server-side by this point, so the old pair is already stale/unusable regardless of what this code does — retaining it would only produce a confusing `invalid_grant` on the next command instead of a clean "no stored OAuth token" state. This is the ONE documented exception to the "leaves the profile's existing credentials completely untouched" invariant above; it does not apply to `jr auth login`'s (Site 1's) equivalent failure, which clears nothing.

- **JSM write-test teardown convention (S-JSM-E2E-2 + S-JSM-E2E-3):** Tests that create JSM requests (Scenarios 5+6+8 and the JSM attachment tests — see `docs/specs/e2e-live-jira-testing.md §4`) self-close via `jsm_self_close(key, &h)` in the test body — NOT via the label-based CI sweeper and NOT via the hardcoded `status_done()` name. Root cause for the helper: the EJ JSM workflow has no transition named "Done" (live run 26839267723 confirmed: tests passed green but left ~2 open EJ tickets). `jsm_self_close` dynamically discovers a closing transition via `jr issue transitions <key> --output json`, selects the first transition with `to.statusCategory.key == "done"` (the stable Jira-wide machine constant for a closing/green status — covers Resolved, Closed, Canceled regardless of workflow name), then attempts resolution discovery (S-JSM-E2E-3): it runs `jr issue resolutions --output json` and passes `--resolution <R>` on the move to produce properly-resolved tickets. Resolution name source: `JR_E2E_JSM_RESOLUTION` env override first, else first `name` from the resolutions list. If resolution discovery fails for any reason, falls back to move WITHOUT `--resolution` (S-JSM-E2E-2 behavior). The `status_done()` helper and its use in ES-project tests remain unchanged — ES Scrum correctly has a transition named "Done". Labels do NOT reliably propagate from `JsmRequestBuilder::build()` to the Jira issue `labels` field, so the sweeper cannot catch EJ-created requests. Self-close is best-effort: all failure paths emit `eprintln!("[WARN] jsm_self_close: …")` and return `()`; the test never fails on close failure. Residual orphan risk LOW and accepted (EJ issues are inert; Resolution-screen transition may still fail; see `docs/specs/jsm-e2e-coverage.md §6.3`). Do NOT extend the sweeper for EJ without first fixing label propagation.
- **JSM resolution proactive enforcement (BC-3.2.013, ADR-0015):** `jr issue move` intercepts done-category transitions BEFORE the POST: in non-interactive mode (`--no-input` or stdin not a TTY), exits 64 with `The transition to "<to_label>" requires a resolution.` + `--resolution` hint. Interactive: `dialoguer::Select` prompt. Supply `--resolution <name>` to send the resolution atomically in the transition body (BC-3.2.011); supply `--no-resolution` to opt out of enforcement. The reactive BC-3.2.009 backstop (API 400 "resolution required") is preserved alongside. Run `jr issue resolutions` to discover available resolution names. See `docs/specs/jsm-e2e-coverage.md §5 Scenario 8` for the E2E enforcement test.
- **`Drop`-guard best-effort teardown pattern (`AttachmentDropGuard`, S-576-6; `ComponentDropGuard`, S-COMP-E2E-1):** live E2E tests that create a fixture needing explicit cleanup (an uploaded attachment, a throwaway `jr component create` fixture) use a small `Drop`-impl struct rather than a bare teardown call at the end of the test function — the struct's field(s) default to `None` (no cleanup performed), are populated IMMEDIATELY after the corresponding creation call succeeds (never before, and never skipped even on an early return — an unpopulated guard performs no cleanup by design), and `drop()` spawns a FRESH `E2eHarness::new()` (never borrows the outer test's own harness, since that borrow would not survive a panic-unwind) to issue the best-effort cleanup call. Every failure path inside `drop()` emits `eprintln!("[WARN] <GuardName> Drop: ...")` and returns — `drop()` must never panic, unlike the test body itself. This is the mechanism that makes cleanup fire on BOTH the normal-return AND panic-unwind paths without duplicating teardown logic at every early-return site. `ComponentDropGuard` (`tests/e2e_live.rs`) is the second instance of this idiom, modeled verbatim on `AttachmentDropGuard`; reach for this pattern (not a bespoke teardown function) for any future E2E test that creates a live-Jira fixture needing explicit deletion.
- **E2E suite maintenance:** The nightly `e2e.yml` schedule (`0 6 * * *` UTC) is a **data-retention guard**, not just a latency optimization: free Jira Cloud sites deactivate after ~120 days of inactivity and have only a ~15–60 day reactivation window before permanent data deletion. If the nightly job fails with HTTP 401, the `JR_E2E_API_TOKEN` secret has expired — Atlassian caps API tokens at 1 year. Rotate the token in the CI service account before expiry and update the secret in the `jira-e2e` GitHub Environment. Annual rotation is required. Runbook: `docs/specs/e2e-live-jira-testing.md` §9.
